# Design — current local prototype

One Python application provides an HTTP UI, CLI and shared SQLite-backed policy core. New local emails enter a persistent queue; a background worker calls Qwen through Groq. The model proposes one structured action. Code validates the schema, binds the action to the server-selected email and determines autonomy. The executor checks policy again before making a local change. The browser never receives API credentials.

## Four autonomy levels

Safe labels and drafts use initial permission without notification, unless notification is relevant. Eligible learned archives execute with notification. Unlearned archives and sends require approval of a specific stored action revision by default. The sole exception is optional Superpowers: after the global current-account toggle is enabled, a qualified Draft Skill revision may authorize an exact matching reply without a per-message approval. Unsupported operations, unresolved human judgment and provider failures stop execution and are handed to the user. Suspected injection blocks mail actions and generates an informational notification; an ordinary approval cannot unblock it.

Payment, permanent deletion, shell commands and bulk mail access are not executable operations. A syntactically valid model response grants no authority. Recipient/text edits invalidate older send approvals and automatic authorization. Local sends are simulated. Live Gmail replies require either approval of the exact saved version or the separately qualified Superpowers authority described below. SQLite atomicity only applies to local operations; Gmail delivery handles uncertain outcomes separately as described below.

## Preference adaptation and Skills

The model's weights are unchanged. Feedback creates a Suggested Skill for Attention, organization, up to two additional labels, draft style or conservative archiving. It has no future effect until the user reviews every displayed example and saves the exact current preview. Ordinary Skill matching and preview are portable across saved Gmail accounts; the stored source account remains provenance, not a match boundary. The preview and live path use the same deterministic matcher, reads already processed mail, makes no model call or mail mutation, labels uncertain cases explicitly and never invents missing contrasts. Sender/similar scope, supported meaning, literal body conditions, result settings and exact-email exclusions can be refined; any edit invalidates prior reviews. Pause preserves a Skill, Resume reactivates it and Delete removes the Skill and its examples while action audit remains. Exact-sender scope remains an address comparison, not authentication.

SQLite also stores explicit archive approvals/rejections by semantic purpose, optionally narrowed to an exact sender. Four initial purposes cover acknowledgements, digests, routine success reports and reference information. Three approvals since the most recent negative feedback are still required before an Archive Skill can execute an eligible archive with notification. Sender-specific experience overrides general experience; explicit keep-in-inbox rules override both. Corrections restore the inbox and reset learning in the chosen scope. Silence and autonomous actions never count as approval.

Archive eligibility also requires no model-indicated action request, deadline, meaningful change, sensitive content, suspicion or notification need, plus a verbatim body quote. This quote only establishes source occurrence: neither it nor the risk flags prove correct understanding. Cross-sender and cross-account transfer increase coverage but can generalize too broadly. The initial taxonomy does not discover new groups or learn subtler boundaries. Archive learning cannot authorize sending or unsupported operations. Each learned archive logs the exact supporting feedback IDs and threshold.

Draft-style memory is separate from action permission. After a user saves a reviewed reply revision, the UI derives its approximate length, greeting presence and sign-off presence. For a changed body, the bounded original/user text pair is also retained as an explicit phrasing example; the UI displays both in the Suggested Skill. An unchanged body requires a separate explicit confirmation that its style works for the user. Send approval alone is never interpreted as style feedback. The user chooses whether that style applies to the same evidenced situation kind across senders or only from the exact sender. A later matching reply proposal is passed through a second constrained Qwen rewrite with the structural rule and, when present, the example pair. The prompt forbids copying situation-specific content, but the rewrite remains probabilistic and may change meaning. It therefore requires exact-version approval by default; merely saving or applying a Draft Skill never enables sending.

Superpowers adds a separate, explicit authority layer. It is globally off by default and bound to the currently verified Gmail account. An exact active Draft Skill revision qualifies for that account only after two successful manual Gmail sends through Wajo where recipient, subject and body were unchanged from the approved saved revision. A future action records which portable Draft Skill revision was applied and binds its potential send authority to the action's actual Gmail account. Editing, rejecting, pausing, deleting or revising the Skill and explicit disable/improve operations revoke or invalidate confirmations. Switching accounts does not transfer the toggle or confirmations to the new account.

Before auto-send is queued and again immediately before delivery, code requires the global toggle, the same qualified Skill revision/account, an incoming Gmail source, a verified unchanged draft, and the exact incoming sender as recipient. Attachments, money/legal/security-sensitive terms, suspicious/sensitive/human-judgment flags, changed content or recipient, and stale permission force review. Automatic results are journaled in Autosent; unknown outcomes are never replayed. This implementation has unit/integration coverage with fixtures, synthetic SQLite databases and mocked Gmail transport only. It has not sent an automatic live reply and has not been exercised in a private-mail pilot.

## Errors and local UI

Inference retries are bounded to two for transient HTTP/transport errors and honor Retry-After within a bounded wait budget. All attempts and redacted error bodies are retained; 403 is not called a quota error. Retries never encompass email sending. Reports containing real input excerpts must stay local.

The UI is loopback-only, checks Host, Origin and CSRF on writes, serves fixed assets and escapes untrusted text under CSP. Counts come from actual mailbox state, and the cards filter the same rows. Queued input survives restarts; core event IDs prevent repeated local effects. A single worker/server per database is required. This is not a public authenticated application.

## Evaluation and remaining work

Unit tests exercise policy boundaries and web requests with adversarial proposals. Live development evaluations classify each synthetic email once, then replay that proposal through fresh and learned policies; this isolates the memory effect and avoids doubling inference costs. Training feedback is supplied by the evaluation's scripted user, and test inputs are separate from training examples. These small developer-written sets were used to refine prompts and are not held-out final evaluation. Full measured results, failures and version distinctions are in `VERIFICATION.md`.

The application runs locally and supports optional real Gmail execution. OAuth, selected-label import and Gmail execution have small live integration checks for earlier manual paths, not classification accuracy measurements. Gmail reconnect/account choice, the ten-label selection limit, cross-account Skills and Superpowers have synthetic and mocked verification only; none has been validated as useful on private mail or through an automatic live send. Follow-up reminders, time-based summaries, a real-mail pilot and final independent evaluation remain future work. Attention/escalation has a small developer-written contrast measurement, not an independent evaluation. No claim of completed take-home or universal injection detection is made.

The application UI and new generated explanations use English (prompt triage-v9). Original email content and exact evidence retain their language. Historical decisions are preserved, and active legacy preferences migrate into managed Skills without turning old one-email feedback into surprise suggestions. Attention, organization, labels, draft style and archive feedback remain separate families; one family's evidence never authorizes another action. Notification preferences and reminder behavior are not implemented.

## Reversible Gmail execution

The web connection panel reuses Desktop OAuth with PKCE and a loopback callback. CSRF-protected POST requests initiate connection and configuration; state reads perform no Gmail I/O. The server fixes OAuth access and import transport from its startup mode, requires explicit Groq consent and the displayed account/mode, and rechecks the account before import, resume, polling, analysis and every write. If OAuth verifies a different account, reads, analysis and synchronization pause until the user keeps previous local data or confirms a displayed-count local reset; the reset never calls Gmail. Initial history supports last 30, last 100, all mail or none, with at most ten optional label IDs that do not constrain future mail. Page cursors, counts, unique Gmail IDs, automatic-sync cursor and Pause/Resume state persist in SQLite. Read polling and Gmail writes share the executor lock, with a fresh client per operation. Failed polling backs off without advancing the cursor. Raw provider errors and credentials are excluded from public state.

Incoming messages are cached separately from analysis jobs. A failed or interrupted model call is not a completed observation: up to four workers retry with persisted backoff and only mark the job done after the complete decision is stored. The Gmail `UNREAD` label is rechecked immediately before analysis as a practical, not authoritative, signal. Mail already read by then may still receive organization and label handling, but proactive attention, archive, draft and escalation actions are suppressed. Incomplete message fetches are locked in the UI and retried no more than once per hour. Sent and user Draft messages are context only; Spam and Trash are excluded. Gmail thread IDs produce one conversation card and a chronological detail timeline. User drafts are never analyzed, edited, treated as feedback or sent by Wajo; Wajo drafts remain versioned and separately identifiable.

Explicit live imports atomically store a trusted account/message/test-label binding alongside the queued email. Action transport is persisted, with old actions defaulting to local simulation. The core writes a durable Gmail operation in the same transaction as the decision or approval. A single-server worker revalidates policy and current mailbox scope before using messages.modify for AI labels or INBOX membership. New live send/draft proposals stage a Gmail draft before any send approval.

Network I/O is outside the database transaction. The operation is first committed as processing, then verified by reading Gmail before local success and positive feedback are recorded. Crashes and ambiguous failures become unknown; no automatic mutation replay occurs. A read-only reconciliation button may confirm the intended state. Corrections reset learning immediately and queue restoration. Failures do not pretend the message was restored. An unused created AI label can remain after partial failure.

This is a single-server design. Concurrent CLI mutations or multiple servers per database are unsupported. Gmail changes between preflight and mutation remain a race; post-read state can subsequently become stale. The implementation cannot atomically lock an external mailbox and SQLite together.

## Exact-version reply delivery

Reply records store recipient, subject, body and a unique per-version marker separately from model output. Draft creation/update and send operations have distinct durable queue keys. Every edit increments the revision; manual approval is unavailable until the draft is saved and verified. An approval hashes the stored outgoing MIME payload and is bound to the action/revision. Automatic authorization separately hashes the same verified bytes and is valid only while its qualified Skill/account/toggle authority remains current. Archive learning never grants send permission.

Before sending, the worker validates current source scope and policy, verifies the saved draft content and includes the approved or automatically authorized MIME bytes in drafts.send. This avoids a draft-edit race substituting different outgoing content. Sending remains a separate user decision unless all Superpowers gates are current. External draft edits or disappearance stop execution. Rejection leaves the unsent Gmail draft available for the owner.

Gmail rewrites draft Message-ID, discovered during live verification. Matching therefore uses the per-revision X-Wajo-Reply-Key and decoded From/To/Subject/Body, rejects extra recipients and attachments, and compares threading headers. A send response ID is saved before readback. Unknown outcomes are reconciled read-only by known ID or a bounded search/scan of Sent; lack of evidence remains unknown, never permission to retry. No exactly-once delivery guarantee is claimed. Independent manual sends, multiple databases, indexing delays and edits/removal of tracking headers are residual limitations. One server per database remains required.

A second live synthetic self-send exercised the manual boundary with real Qwen: the user changed draft revision 1, saved and verified revision 2, then explicitly approved it. Sent readback matched the exact approved fields and body. This verifies the manual transport and permission path only; it does not establish general reply quality or validate Superpowers auto-send.

API basis: [Google draft creation/update/send guide](https://developers.google.com/workspace/gmail/api/guides/drafts), including supplying approved MIME in the send request.

## Explicit label and attention preferences

Label feedback is stored separately from archive approvals. Versioned reviews change the current email and may propose an account/kind/sender-scoped Skill. An active Skill can carry one or two additional AI labels. A third-label result becomes an explicit conflict: existing labels remain unchanged until the user selects exactly two. Topic and Subtype are separate and do not consume this limit; unrelated Gmail labels are preserved. Unknown external outcomes are not retried automatically. A finite model-classified purpose taxonomy groups paraphrases; an exact evidence quote is required before applying a label Skill. This is explicit preference memory, not model fine-tuning. Sender-specific Skills override general Skills.

Attention is an explicit visibility preference with its own feedback history and email/similar/sender scope. Similarity uses a separate semantic attention cue plus an exact evidence quote, not a hard Topic/Subtype match. A match surfaces mail in **Needs attention** and prevents learned automatic archiving, but does not change autonomy to Notify, mark the email Important or create/suppress an escalation. Exact-sender scope is an address filter, not proof of sender authenticity. No label or organization name changes hard action permissions.

Topic, subtype and importance form a separate local organization layer. The finite evidenced situation kind supplies a conservative initial topic/subtype pair. A user edit can apply to one email or propose a Skill for that kind across senders or from one exact sender; the narrow active Skill wins. Importance is a boolean user marker rather than a mandatory model-generated scale. These fields do not change Gmail labels, attention, action selection or permissions. A 12-case development contrast check measured correct kind classification and transfer for selected preferences, but it is small and developer-written; independent model-quality evaluation remains required.
